# Опциональные задачи по ядру магазина

Ниже задачи, которые остались после cleanup `ShopInstance`, `ShopOffer` и `ShopTable`. Они не являются срочными багфиксами, но могут улучшить API и подготовить код к будущему редактору с сессиями.

## Опционально: явное добавление и замена магазинов

Сейчас `ShopTable.addShop(instance)` может заменить магазин с тем же id без явного сигнала вызывающему коду. Для админки и editor session лучше разделить сценарии:

- `addShop(...)` — добавляет только новый магазин и возвращает `false`, если id уже занят.
- `replaceShop(...)` — явно заменяет существующий магазин.
- `putShop(...)` — универсальный метод, если нужна текущая семантика.

Это снизит риск случайно затереть магазин при командах, импорте или применении editor session.

## Опционально: точечный reindex категорий

Сейчас изменение любого компонента внутри `ShopOffer` вызывает обновление parent shop и пересборку категорий. Это безопасно, но грубовато: изменение цены, имени или награды тоже запускает `reindexCategories()`.

Позже можно сделать отдельный путь для изменения `CatalogComponent`:

- обычное изменение offer — только dirty/cache invalidation;
- изменение catalog/id/uuid — dirty/cache invalidation + reindex категорий.

Такой подход уменьшит лишнюю работу при массовом редактировании офферов.

## Опционально: debounce/batched autosave

Autosave сейчас срабатывает через `onUpdate` и может ставить сохранение в очередь на каждое изменение. Для обычных правок это нормально, но editor session лучше делать иначе:

- помечать магазин dirty;
- сохранять периодически, пачкой или при явном `accept/apply`;
- не сохранять промежуточные состояния, пока админ ещё редактирует магазин.

Это хорошо ложится на будущую архитектуру редактора с черновиком и подтверждением изменений.

## Опционально: атомарный reload guard

`ShopTable.reload()` сейчас защищён через `volatile boolean reloading`. Если reload может прийти с разных потоков, лучше заменить guard на `AtomicBoolean.compareAndSet(false, true)` или сделать метод `synchronized`.

Это уберёт race condition, когда два reload могут одновременно пройти проверку `if (reloading) return`.

## Опционально: явная семантика transient/persistent shop

`shouldSave` теперь реально используется, но семантика всё ещё может быть неочевидной: `save(instance)` для transient shop просто ничего не делает.

Можно сделать API более читаемым:

- `addPersistentShop(...)` — добавить и сохранять изменения;
- `addTransientShop(...)` — добавить только в память;
- `setPersistent(boolean)` или `isPersistent()` вместо `shouldSave()`.

Так будет проще отличать временные магазины, тестовые магазины и реальные сохранённые магазины.
